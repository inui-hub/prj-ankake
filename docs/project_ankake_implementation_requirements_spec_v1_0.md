# Project Ankake 実装要件仕様書 v1.0

更新日: 2026-07-24

---

# 1. 本仕様書の目的

本仕様書では、Project Ankakeの初期実装における実行環境、公開方式、データ保存方式およびCPU対戦処理の基本方針を定義する。

ゲームルール、カード処理および各画面の詳細要件は、以下の既存仕様書に従う。

- 基本ルール要件仕様書
- カード詳細要件仕様書
- カード一覧
- 画面要件仕様書
- 各画面詳細要件仕様書

本仕様書では、具体的なソースコード、フォルダ構成、クラス構成およびAPI設計は定義しない。

---

# 2. 初期実装の範囲

初期実装では、以下を実装対象とする。

- メニュー画面
- デッキ構築画面
- 対戦準備画面
- CPUとの1対1対戦
- 対戦画面
- カードおよびトークン
- 基本ルールに基づく対戦進行
- ルールベースで動作するCPU
- 保存済みデッキのローカル保存

# 3. 実行および公開方式

## 3.1 Webアプリケーション

Project Ankakeは、ブラウザ上で動作するWebアプリケーションとして実装する。

プレイヤーは、公開されたURLへアクセスしてゲームを起動する。

初期実装では、専用アプリケーションのインストールを必要としない。

## 3.2 GitHub Pages

本仕様書の実装範囲では、GitHub Pagesで公開する。

GitHub Pagesで配信可能な静的ファイルのみで動作する構成とする。

以下のサーバ側機能は実装しない。

- Node.jsなどによる常時稼働サーバ
- サーバ側API
- サーバ側データベース
- サーバ側セッション
- サーバ側でのゲーム進行処理

## 3.3 ブラウザ内で行う処理

以下の処理は、すべて利用者のブラウザ内で実行する。

- 画面表示
- プレイヤー操作の受付
- ゲーム状態の管理
- ゲームルールの判定
- カード効果の処理
- 共鳴処理
- アタックフェーズの自動処理
- 勝敗判定
- CPUの思考および操作
- デッキデータの保存と読み込み

# 4. 対応環境

初期実装では、PC向けの一般的なモダンブラウザを対象とする。

主な対象は以下とする。

- Google Chrome
- Microsoft Edge

スマートフォンおよびタブレットでの操作最適化は、初期実装の必須要件としない。

# 5. データ管理

## 5.1 カードマスタ

カード、トークンおよび盤面に関する固定データは、Webアプリケーションの静的データとして配信する。

固定データの変更は、Webアプリケーションの更新として反映する。

## 5.2 デッキ保存

作成したデッキは、ブラウザのローカル保存領域へ保存する。

保存先にはIndexedDBを使用する。

保存したデッキは、同じ端末、同じブラウザおよび同じ公開URLからアクセスした場合に利用できる。

## 5.3 保存データの制約

初期実装では、以下を行わない。

- ユーザーアカウントとの紐付け
- 異なる端末間での同期
- 異なるブラウザ間での同期
- クラウドへのバックアップ
- サーバへのデッキ保存

ブラウザのサイトデータが削除された場合、保存済みデッキが失われる可能性がある。

## 5.4 対戦状態

対戦中のゲーム状態はブラウザのメモリ上で管理する。

初期実装では、対戦途中の保存および再開を行わない。

ページの再読み込みまたはブラウザの終了によって対戦状態が失われた場合、その対戦は終了したものとして扱う。

# 6. ゲーム処理の基本方針

## 6.1 ルール処理の統一

プレイヤーとCPUは、同一のゲームルール処理を使用する。

CPU専用の召喚条件、移動条件、カード効果または勝敗条件は設けない。

召喚、移動、スペル発動およびその他の操作について、実行可能かどうかは基本ルールおよびカード詳細要件に従って判定する。

## 6.2 画面表示との分離

ゲームのルール判定と画面表示は、論理的に分離する。

画面表示はゲーム状態を参照して描画し、画面側だけでPP、手札、盤面、共鳴値または勝敗状態を独自に変更しない。

ゲーム状態の変更は、ゲームルール処理を通して行う。

---

# 7. CPU実装方式

## 7.1 基本方式

CPUはルールベース方式で実装する。

初期実装では、以下を使用しない。

- 機械学習
- 強化学習
- 大規模言語モデル
- 外部AIサービス
- 対戦結果を利用した自動学習

CPUの強さおよび思考方式は1種類とする。

## 7.2 CPUが参照できる情報

CPUは、CPU自身が通常の対戦ルール上確認できる情報と、公開情報のみを参照する。

CPUは以下の非公開情報を参照してはならない。

- プレイヤーの手札内容
- プレイヤーまたはCPUのデッキ内のカード順
- 次にドローするカード
- 未確定の乱数結果

CPUは、自身の手札内容を参照できる。

## 7.3 CPUの操作対象

CPUは自分のプレイフェーズ中に、以下の操作を行う。

- クリーチャーの召喚
- クリーチャーの移動
- スペルの発動
- プレイフェーズの終了

アタックフェーズは基本ルールに従って自動処理し、CPUは攻撃対象および攻撃順を選択しない。

## 7.4 合法な操作の選択

CPUは、現在のゲーム状態から実行可能な操作候補を取得する。

実行不可能なカードの使用、召喚、移動または対象選択を行ってはならない。

操作候補の判定には、プレイヤー操作と同じゲームルール処理を使用する。

## 7.5 操作候補の評価

CPUは、実行可能な操作候補をルールベースで評価し、評価結果が最も高い操作を選択する。

評価では、少なくとも以下を考慮する。

1. 勝利条件を成立させられるか
2. 相手の勝利条件成立を防げるか
3. 敵プレイヤー拠点へ与えられるダメージ
4. 中立拠点の制圧および防衛
5. 味方クリーチャーと敵クリーチャーの戦力差
6. クリーチャーの位置および攻撃可能範囲
7. カード効果によって得られる利益
8. 共鳴値および共鳴効果
9. 手札と使用可能PP
10. 次のアタックフェーズで発生する結果

勝利できる操作が存在する場合は、その操作を最優先する。

## 7.6 CPUターンの進行

CPUは、選択した操作を1つ実行するたびに最新のゲーム状態を確認し、次の操作を再判定する。

以下のいずれかを満たした場合、プレイフェーズを終了する。

- 有効な操作候補が存在しない
- 残りPPで実行できる有効な操作がない
- 操作を続けるよりプレイフェーズを終了した方が評価が高い
- CPUの処理上限に到達した

CPUがプレイフェーズを終了した後、アタックフェーズを自動処理する。

## 7.7 同評価時の処理

複数の操作候補が同じ評価となった場合は、あらかじめ定めた固定の優先順位または乱数によって1つを選択する。

乱数を使用する場合でも、実行可能な操作候補の中から選択する。

## 7.8 CPU処理中の画面

CPUの思考中および操作中は、CPUターンであることを画面へ表示する。

CPU処理によって、画面表示や演出が長時間停止しないようにする。

CPUの操作結果は、プレイヤーの操作結果と同様に盤面および戦況ログへ反映する。

---

# 8. エラー時の扱い

デッキデータの保存または読み込みに失敗した場合、エラー内容をプレイヤーへ表示する。

ゲーム処理中に継続不可能なエラーが発生した場合は、対戦を停止し、対戦準備画面またはメニュー画面へ戻れるようにする。

画面側だけで失われたゲーム状態を推測して復元してはならない。

---

# 9. 初期実装の対象外

初期実装では、以下を対象外とする。

- オンライン対戦
- 対戦用サーバ
- ユーザー登録およびログイン
- クラウドセーブ
- 端末間同期
- ランキング
- マッチメイキング
- 観戦
- リプレイ保存
- 対戦途中の保存および再開
- CPU難易度の選択
- CPUの自動学習
- スマートフォン向けの操作最適化
- 不正操作防止を目的としたサーバ側検証

# 10. 将来拡張への考慮

本仕様書の実装範囲はGitHub Pages上で完結させるが、ゲームルール処理は画面固有の処理へ直接依存させない。

将来オンライン対戦など本仕様書の範囲外の機能を検討する場合は、別途要件を策定する。

本仕様書の実装範囲では、ゲームルール処理、CPU処理およびデッキ保存処理をブラウザ内で完結させる。
